File Systems: Organization and Access

A file system is the operating system component that organizes, stores, retrieves, names, and protects data on persistent storage. From a process's point of view, the file system presents a uniform abstraction -- files and directories -- that hides the underlying complexity of physical storage devices, block addressing, and free-space tracking.

A file is a named collection of related data, treated by the OS as the smallest logical unit of persistent storage. Every file has attributes tracked by the OS independent of its contents: a name, a type, its size, timestamps for creation/modification/access, ownership and permission information, and a location pointer to where its data actually lives on the storage device. Directories are themselves special files that map human-readable names to the underlying file entries, and are organized hierarchically (a tree of directories containing files and further subdirectories) in virtually every modern OS, letting users and programs organize files into a logical namespace independent of physical disk layout.

Internally, file systems track which disk blocks belong to which file using one of a few classic allocation strategies. Contiguous allocation stores each file's blocks sequentially on disk, which gives excellent read performance (minimal seek time, and even a single I/O request can read the whole file) but suffers from the same external-fragmentation problem as contiguous memory allocation, since files grow and shrink and disk space becomes fragmented over time. Linked allocation stores each file as a linked list of blocks scattered anywhere on disk, with each block holding a pointer to the next; this eliminates external fragmentation and makes files trivial to grow, but random access is slow (you must traverse the chain from the start) and a single corrupted pointer can lose the rest of the file. Indexed allocation (used by most modern file systems in some form) keeps a separate index block per file listing all of its data block locations, combining fast random access with flexible growth, at the cost of the extra space and indirection needed for the index structure itself.

File handles are the OS's runtime bookkeeping for files a process currently has open: when a process opens a file, the OS allocates a file handle (a small integer or descriptor) that refers to an open-file table entry tracking the current read/write position, access mode, and a reference to the underlying file's on-disk location. File handles are a limited resource -- each process, and the system as a whole, can only have a bounded number of files open simultaneously -- which is why leaking file handles (opening files without closing them) is a classic resource-exhaustion bug, directly analogous to the CPU, memory, database-connection, and network resources tracked elsewhere in an OS resource manager.

File system metadata -- the directory structure, free-space bitmap or free list, and per-file attribute records -- must remain consistent even across crashes, which is why production file systems use journaling (writing intended changes to a log before applying them, so an interrupted operation can be replayed or rolled back on recovery) or copy-on-write techniques. This mirrors, at the storage layer, the same reliability concern that process/resource managers address at the execution layer: the system must be able to detect an inconsistent or partially-completed state and recover to a consistent one rather than silently corrupting data.
