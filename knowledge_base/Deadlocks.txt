Deadlocks: Conditions, Detection, Avoidance, and Recovery

A deadlock is a state in which a set of processes are each waiting for a resource that is held by another process in the same set, so that none of them can ever proceed. Deadlocks are a fundamental hazard whenever multiple processes compete for exclusive-access resources (memory, file handles, database connections, locks, network sockets) and are allowed to hold some resources while requesting others.

Coffman's four necessary conditions must all hold simultaneously for a deadlock to occur. Mutual exclusion: at least one resource must be held in a non-shareable mode (only one process can use it at a time). Hold and wait: a process holding at least one resource is waiting to acquire additional resources currently held by other processes. No preemption: resources cannot be forcibly taken away from a process; they must be released voluntarily. Circular wait: there exists a cycle of processes P1, P2, ..., Pn where P1 waits for a resource held by P2, P2 waits for one held by P3, and so on until Pn waits for one held by P1. Breaking any single one of these four conditions is sufficient to prevent deadlock, which is why real systems mix strategies (e.g. allowing preemption in some subsystems, or enforcing a strict resource-acquisition ordering to prevent circular wait).

Deadlock detection works by modeling the system as a resource-allocation graph (or, equivalently, a "waits-for" graph among processes): a directed edge from process A to process B means A is waiting for a resource currently held by B. A deadlock exists if and only if this waits-for graph contains a cycle. Detecting a cycle is a standard graph algorithm: a depth-first search that tracks each node's color (unvisited / currently-on-the-recursion-stack / fully-processed) will find a cycle whenever it encounters an edge back to a node that is still on the recursion stack (a "back edge"). This is more general and correct than merely checking pairwise mutual waits, because deadlocks frequently involve three or more processes in a longer cycle rather than just two processes blocking each other directly.

Deadlock avoidance takes a more proactive stance than detection: rather than letting the system enter a potentially unsafe state and checking afterward, the OS evaluates each resource request in advance and only grants it if the resulting state is still "safe" -- meaning there exists at least one ordering in which every process can still obtain enough resources to finish and release its holdings. The classic algorithm for this is Banker's Algorithm, named by analogy to a banker who will only extend a loan if enough capital remains to satisfy at least one customer's maximum possible need, ensuring the bank never runs out of money with everyone still owed. A simplified variant checks, before granting an allocation, whether at least one other process with a declared maximum need could still be fully satisfied from the resources that would remain -- if not, the request is denied even though enough resources exist right now, because granting it could lead to an unsafe state later.

Deadlock recovery is the reactive strategy: once a cycle is detected, the system must break it. The standard approach is process termination -- killing one or more processes in the cycle (typically choosing the lowest-priority or least-progressed one to minimize wasted work) so that the resources it holds are released back to the pool, which in turn allows the remaining processes in the cycle to proceed. An alternative is resource preemption -- forcibly taking a resource away from one process in the cycle and giving it to another -- but this requires the resource and the process's state to support being safely rolled back, which not all resources allow.
