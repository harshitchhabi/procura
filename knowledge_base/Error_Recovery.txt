Error Detection and Recovery Strategies in OS Design

Operating systems are built on the assumption that failures are normal, not exceptional: processes crash, resource requests fail, hardware misbehaves, and schedules go wrong. A robust OS does not simply propagate these failures to the user -- it detects them, classifies them, and applies a recovery strategy appropriate to the failure type, logging enough detail that the failure can be diagnosed after the fact.

Detection is the first stage: the system must actively recognize that something has gone wrong rather than assuming success. Three common categories of failure map directly onto observable, checkable conditions. A burst-time anomaly is detected when a process has been running far longer than its declared/expected burst time while system resource usage remains high -- a strong signal that the process is stuck in a loop, deadlocked, or otherwise misbehaving rather than legitimately doing more work than estimated. A memory allocation failure is detected the moment a request exceeds currently available memory -- this is a simple, immediate check against the resource manager's live state. A deadlock is detected by finding a cycle in the system's waits-for graph, as described in the Deadlocks reference -- this requires proper graph cycle detection (e.g. depth-first search with recursion-stack tracking) rather than only checking for simple pairwise mutual waits, since real deadlocks often involve chains of three or more processes.

Diagnosis follows detection: once a failure is flagged and classified by type, the system should produce a plain-language explanation grounded in both the specific incident (which process, what resource, what values) and general domain knowledge about that failure category. Retrieval-augmented explanation -- pulling the most relevant reference material about the failure type and combining it with the live incident data -- produces diagnoses that are both accurate (grounded in real OS concepts, not fabricated) and specific (tied to what actually happened), which is far more useful for debugging than a generic error code.

Recovery is the reactive response, and different failure types call for different rule-based scripts. For a memory allocation failure, the standard response is to suspend a lower-priority process that is currently holding memory, release its allocation back to the pool, and retry the original failed request. For a timeout (a process that has overrun its expected time budget), the standard response is to stop the process, log the incident, and retry it -- returning it to the ready queue so the scheduler gives it another chance, often with adjusted expectations. For a crash (a process that has entered an invalid or unrecoverable state), the standard response is to save the error details, restart the process from a clean state, and increment a retry/error counter so that a process which repeatedly crashes can eventually be flagged for permanent termination rather than restarted forever. For a deadlock, the standard response -- since prevention already failed and avoidance was not applied in time -- is recovery by termination: kill the lowest-priority process participating in the detected cycle, release all of the resources it was holding, and resume the remaining processes in the cycle, which are now free to proceed since the circular wait has been broken.

A well-designed recovery engine keeps a complete audit trail: every detected error, its diagnosis, and the recovery action taken should be logged with enough detail (timestamps, affected process IDs, raw incident data) to support post-mortem analysis, to detect recurring problem patterns (e.g. the same process repeatedly triggering memory failures, suggesting its declared memory_requirement should be revisited), and to build user trust that automated recovery actions are transparent rather than a black box.

Runbooks are the industry term for predefined recovery scripts. Tools such as PagerDuty Runbook Automation (built on Rundeck) and AWS Systems Manager Automation run named, parameterised, auditable steps, and AWS classifies each step as Mutating, Non-mutating or Undetermined so that risky steps can require human review. Procura follows the same safety pattern: the AI only explains a failure, while a fixed, pre-defined script decides and performs the recovery action.

Procura's memory-failure recovery follows rules modelled on Kubernetes preemption, which only evicts lower-priority pods and only when doing so lets the pending pod be scheduled. First, retry: if memory has already been freed since the failure was detected, the allocation is simply retried. Second, suspend_and_retry: a holder is suspended only if it has strictly lower effective priority than the failing task and freeing its memory would actually make the allocation fit. Otherwise, memory_failure_no_victim: the task is left pending rather than evicting higher-priority work, or evicting a task for no benefit.

These rules prevent two pathologies seen in naive recovery engines. Without the priority rule, two tasks can repeatedly evict each other, a ping-pong similar to thrashing. Without the fit check, a task can be suspended without freeing enough memory to help. Without the retry step, the engine acts on stale findings, because all failures in a detection pass are recorded before any recovery runs.

Grounded diagnosis: the AI diagnosis is given the recorded incident facts, such as the memory requested versus memory available, the recovery action executed, and the current resource state, as an authoritative section of its prompt. Research on LLM root-cause analysis, such as SynergyRCA, found that retrieval over structured system state is more reliable than retrieval over flat text, which can be topology-blind and lead the model to invent plausible but false causes.
